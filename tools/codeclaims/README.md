# codeclaims

`codeclaims` scans a local repository without importing or executing its code and checks structured claims against the resulting facts. Python 3.11 or later and Git (for Git metadata) are required; there are no runtime packages or network calls.

Install with `pipx install ./tools/codeclaims`, or run `python -m codeclaims` from this directory. The included `codeclaims.cmd` and `codeclaims.ps1` launchers also run from this directory or an environment where the package is installed.

```text
codeclaims scan --repo /path/to/repo --out /path/to/output --exclude 'auth/**' --max-md-tokens 15000
codeclaims check --facts /path/to/output/codefacts.json --in claims.jsonl --out results.jsonl
```

Scan writes `codefacts.json`, a capped `codefacts.md`, `markers.jsonl`, and `errors.jsonl`. The optional `--config file.toml` accepts `repo`, `exclude` (an array), and `max_md_tokens` at the top level or in `[codefacts]`; command-line settings take precedence, and exclusions are additive. `.git`, `.venv`, `venv`, `node_modules`, `__pycache__`, and files beginning `.env` are always excluded. Add credential directories such as `auth/**` with `--exclude`; files in excluded directories are not opened. Results are redacted, but review them before sharing.

For a Git repository, `--repo` must identify the outermost enclosing worktree root. Nested directories, including nested repositories or submodules with their own `.git` marker, are refused with exit code 2 before scanning or copying source contents, so exclusions always use the supplied root. A linked worktree outside another worktree is supported. Non-Git directories are supported. `check` also refuses saved facts that identify a nested Git directory; rescan from the outermost worktree root with exclusions relative to that root. Output validation independently protects every enclosing worktree.

Markdown preserves section priority and reserves every section's count heading plus omission counts pointing to the artifact and key containing the missing facts. Env and settings omissions point to their separate JSON keys; markers point to `markers.jsonl`. The 15-commit and 40-marker detail limits also report the omitted counts. Marker totals count records, with separate summaries by kind and top-level directory. A cap too small to fit this minimum summary exits with code 2, reports the minimum required for that scan, and writes no output files. The cap uses the estimate of one token per 3.5 characters.

Each input line is a JSON object such as `{"id":"example","claims":[{"kind":"route","value":"GET /items"}]}`. Supported kinds are `path`, `symbol`, `route`, `env`, `table`, `migration`, `test`, `dep`, `tf`, and `text`. Output is JSONL with a verdict and locations or near matches. A missing result is not proof that a claim is false; text searches examine at most 200 eligible files. Scan and check read repository files but never modify them. Both commands require outputs outside the source repository and outside `~/.codex` and `~/.claude`, including after resolving filesystem links; existing hard-linked output files are refused. Other user-selected external output locations are supported. Invalid output locations exit with code 2 before any output is written. Other I/O errors exit with code 3, and successful commands exit with code 0.

If redaction changes the source repository path in the saved facts, `check` refuses those facts with exit code 2 before processing claims or writing output. The displayed path cannot safely identify the original repository for text reads or output-location checks. Rescan from a repository path without sensitive identifiers to use `check`; no unredacted path or reversible path encoding is saved.

Routes resolve static router imports and aliases by module, including nested routers and multiple registrations. Dynamic prefixes and registration cycles are marked unresolved. SQLModel classes count as ORM models when `table=True` or an explicit table name is present. Migrations come from `migrations/versions` and the repository's `alembic.ini` locations (`script_location`, or `version_locations` when supplied); external locations are ignored.

Git queries disable optional index writes, fsmonitor commands, hooks, signature verification, and lazy fetching. All queries use disposable metadata built by reading Git's metadata files directly, without loading local config includes or clean/process filter settings. Status runs against temporary copies of eligible non-asset files; excluded credentials, `.env*` files, excluded attributes/ignore files, and all files under any `templates` or `static` directory never enter that worktree. Asset contents are never read by Python or Git; scan lists their paths and sizes only. Excluded paths are omitted from dirty results too. Git metadata (the index, refs, HEAD, object database, and the local config's object-format setting) remains necessary for repository history and status; configuration includes are never followed. Symlinks and Windows junctions are skipped.

For assets, dirty status preserves staged changes and tracked deletions. It detects tracked size changes using cached sizes from ordinary Git indexes (versions 2, 3, and 4). When content cannot be determined from size, the worktree status position is `?` (for example ` ?` or `M?`): this means a **possible change**, including clean and same-size edited assets, not a confirmed modification. Markdown labels these rows as possible and counts them as “dirty or possible files”; JSON includes `git.status_notes`. Untracked assets are explicitly reported as `??` using index membership and filesystem metadata only. Asset ignore rules are not evaluated, so ignored untracked assets may also be included. A staged deletion followed by an untracked replacement has separate deletion and `??` records. With split, unsupported, or unreadable indexes, present assets receive `?` because content and possibly tracking are unknown. No asset status requires reading asset contents.

Text claim searches revalidate saved file paths at check time. Resolved asset/excluded paths and symlinks or Windows reparse points in any path component are skipped, including directory aliases introduced after the scan.

Dirty submodules are checked with their own sanitized metadata and eligible copies, including nested exclusions, then their dirt is propagated to the parent. Git separately detects changed submodule commits. Excluded files cannot make an otherwise clean submodule appear dirty. Dirty detection compares files without custom filters, so filter-dependent repositories can show modifications that ordinary Git status considers clean. Only eligible `.gitignore` rules are available; global ignore rules and `.git/info/exclude` are omitted. Copying eligible files needs temporary disk space proportional to their size. Temporary data is removed after each query; if the configured temporary root lies in the source tree or protected agent settings, Git metadata is omitted.
